Applies to the `reminders-instructions-enhancements` workflow only (`.ai-sdd/workflows/reminders-instructions-enhancements.yaml` — the full-feature pipeline as generated by the ai-sdd scaffold, 2026-10-25; `risk_tier: T1` defaults). The project constitution (`/constitution.md`) is inherited unchanged — Architecture Constraints 1–6, the safety-critical constraints, Standards, release gates, and Agent Principles all bind this feature. **Safety delta: none.** This supplement does not restate project-level rules; it records only what the feature adds, what it must not change, and the decisions left open. It claims no new safety-critical surface.

Source of truth: the owner's scaffold brief (2026-10-25) and its clarifications, restated under Feature Purpose & Scope. Reference material: `requirements-dementia-supplement.md` §1.9 (FR-D26–D29, caregiver-configured routine blocks — the broader routine-guidance requirement this feature begins to serve) and the existing `RoutineEntry`, `VisualAidStore`, `RoutineVisualAidFireHandler`, `EventExtrasStore`, `FreeFormEventService`, and `FreeFormEventFireHandler` code documented below.

## Feature Purpose & Scope

Purpose: let a caregiver attach an **instruction — written text, an image, or a video** — to a reminder or calendar event so the elderly user can see how to do the activity at home when the reminder fires. Motivating example: a physio exercise reminder carries a video of the exercise performed at home. **Media amendment (owner 2026-10-25):** all three media kinds from the original brief are in scope — text instructions, image instructions, and video instructions. Video remains the flagship path; text and image are first-class kinds, not placeholders.

Project purpose and target users are inherited unchanged (root §Project Purpose, §Target Users): the primary user is the elderly person (60+, many with cognitive or motor challenges including tremors, non-English first language); the secondary user is the adult-child caregiver/spouse who configures reminders and events on their behalf.

Observable success — **CONFIRMED (OD-8, owner 2026-10-25)**: a caregiver can attach an instruction (text, image, or video) to a routine reminder or free-form event, and when the reminder fires the elderly user can follow the instruction in the app without caregiver help at that moment.

In scope:

1. **Daily-routine reminders** configured in the Settings Reminders tab — `RoutineSettingsView`, the `RoutineEntry`/`VisualAid` model, `VisualAidStore`, `RoutineVisualAidFireHandler`, and the `NotificationFacade`/`AppCoordinator` wiring.
2. **Free-form calendar events** — `EventsView`, `FreeFormEventService`, `EventExtrasStore`, `FreeFormEventFireHandler` (owner: instructions apply "to freeform calendar events too").
3. **Local video as the primary path**: pick an existing video from the phone's library, or record one in the app. Both sources are first-class.
4. **All three instruction kinds are in scope** (owner 2026-10-25): a text instruction (the written steps, stored as text in the encrypted payload), an image instruction (photo/diagram, following the existing `VisualAid` photo path), and a video instruction. An optional caregiver-written caption accompanies image and video (same role as `VisualAid.caption`); a text instruction is itself the text. Audio-only instructions are NOT required.
5. **In-app playback at fire time**, usable by the elderly user unaided.

Out of scope (must not change):

- **Medication reminders** — separate and in-flight; no video instruction surface is added there, and no medication code path is altered.
- **Imported / Google / other-calendar events** — only app-created free-form events are tracked by `EventExtrasStore`; membership in that side index is what "one of ours" means.
- **Any new acknowledgement, escalation, re-fire, or missed-event machinery.** Routine reminders and free-form events are explicitly non-safety-critical (`RoutineEntry.swift:77–80`: "no acknowledgement window, no escalation, no re-fire — those stay exclusive to `MedicationScheduler`").
- **Voice/TTS narration, transcript generation, and voice authoring of instructions** — not in the brief.
- **Android (v2)** and any cloud upload, transcoding, or AI processing of instruction video.
- **YouTube links as the primary path** (see OD-3).

## Instruction Model & Storage Contract

Verified ground truth:

- `RoutineEntry.visualAids: [VisualAid]` stores a bare `filename` plus an optional `caption` — never a path, never bytes (`RoutineEntry.swift:62–75`, `:100`). Files live at `Application Support/VisualAids/<entryId>/<file>.jpg` (`VisualAidStore`), written with `.completeFileProtection` (`VisualAidStore.swift:123`). Deleting the entry drops the whole folder (`RoutineScheduler.removeEntry` → `visualAidStore.deleteAll`, `RoutineScheduler.swift:111–117`).
- Free-form events keep one `photoFilename` in `EventExtras`, an encrypted side index (`EventExtrasStore`), while the bytes live in `ContactPhotoStore(directoryName: "EventPhotos")` (`FreeFormEventService.swift:272`). Event deletion and the vanished-event reconcile delete the index row and the file together (`FreeFormEventService.swift:293–315`, `:424–431`). `EKEvent` has no attachment API.
- Both models use tolerant decoders so pre-feature payloads load (`RoutineEntry.swift:135–145`; `EventExtrasStore.swift:41–45`).

Binding properties:

1. **Video instructions are app data, not Photos library assets.** They live in the app's Application Support tree under a video sibling of the existing photo layout (a dedicated root such as `Application Support/InstructionVideos/<entryId>/` for routines, and a separate event root — exact paths OD-5). They are never saved to the Photos library, never appear in the photo picker, and are never shared to other apps. This preserves the privacy/lifecycle property the photo aids already hold: the instruction dies with the reminder it belongs to.
2. **The model stores only bare file names / identifiers, never bytes.** The encrypted payload (`RoutineEntry` via `RoutineStore`/`EncryptedLocalStorage`; `EventExtras` via `EventExtrasStore`) stays small. Video bytes are protected at rest by iOS file protection (`.completeFileProtection`, the class the photo aids use), not by `EncryptedLocalStorage` — that store is documented for small payloads, and playback must be able to start without a Keychain round trip.
3. **Migration rule.** New model fields are optional with custom-decoder defaults; pre-existing `RoutineEntry` and `EventExtras` payloads must keep loading. Never lose a household's reminder list or event index to a missing key. The existing `decodeIfPresent` patterns are the precedent.
4. **One instruction belongs to the entry/event, not the occurrence.** The same video is offered at every firing; editing it takes effect for future firings without re-creating the reminder. For routines, instruction edits follow the existing `setVisualAids` / `persistAndReschedule` path (`RoutineScheduler.swift:131`), so a video edit and a time edit take the same durable, re-armed path. A video-only entry must be as valid as a photo-only one.
5. **Delete/replace lifecycle is transactional in the direction that cannot lose data.** A replacement video is written before the index points at it; the old file is deleted only after the index update succeeds (the `FreeFormEventService.setPhoto` precedent, `:396–414`). A failed write leaves the previous instruction intact and reports the failure plainly. Deleting the owning routine/event — and the free-form reconcile dropping a vanished event — must delete the video file too, leaving no orphans.
6. **Instruction media never enters the notification attachment store.** `UNNotificationAttachment` moves the file it is given, which is why the existing routine path copies the first photo per occurrence (`RoutineAlarmScheduler.swift:108–143`). Videos stay in the app store; the notification remains today's text banner (plus the existing first-photo attachment). This also avoids copying a large file on every re-arm.
7. **Filename hygiene.** Store plain, traversal-free file names under a per-entry directory, matching `VisualAidStore.fileURL` / `isPlainFilename` (`VisualAidStore.swift:237–249`). A hand-edited payload must never smuggle a path out of the store root.

## Capture & Permissions Contract

1. **Two primary sources, both local:** pick an existing video from the library (the `PHPickerViewController` / `PhotosPicker` pattern, which needs no photo-library permission because it runs out of process — `VisualAidStore.swift:26–30`, `EventsView.swift:295`), and record a new video in the app. Library pick remains first-class even when the camera is unavailable or denied.
2. **Recording is the only new permission surface.** Camera and microphone are requested at the point of use with plain-language explanation (root compliance constraint). The app must work fully if either is denied — the library path and the reminder itself are unaffected. `Info.plist`'s `NSCameraUsageDescription` (`:113`) and `NSMicrophoneUsageDescription` (`:121`), which currently describe medication/appliance photos and voice commands, must be amended to disclose video recording and that the recording stays on the device. Whether recording ships in v1, and whether it uses the system camera UI or a custom capture UI, is OD-2.
3. **The caregiver's edit surface stays the existing one.** Routine instructions are managed from the routine's manage row in `RoutineSettingsView` (the sheet opened by the photo button, `:107–116`); event instructions from the free-form event form/detail (`EventsView`). No new standalone media-library screen.
4. **Feedback is visible and plain.** Choosing, recording, saving, replacing, and removing a video each produce a clear state in the caregiver UI; cancellation is an outcome, not an error. Save failures keep the draft or the previous instruction and say so — never a silent no-op.
5. **Captions are optional, caregiver-authored, and shown with the video** at the user's reading size/direction; a blank caption reserves no space (the `VisualAidDisplayState.currentCaption` rule, `:61`).
6. **Localisation and elder-first sizing.** All new UI strings are externalised (en + ne in `Localizable.xcstrings`). Caregiver screens still follow elderly-first sizing: ≥44pt targets, ≥18pt body text, high contrast, plain language.

## Fire-Time Playback, Accessibility & Failure Contract

Verified ground truth:

- Routine fires deliver through `UNRoutineNotificationScheduler` and the shared `NotificationFacade`. `RoutineVisualAidFireHandler.willPresent` presents the full-screen elder-facing screen only when the entry has visual aids, and **always returns `false`** so it can never mute the read-aloud or caregiver handlers (`RoutineVisualAidFireHandler.swift:15–18`, `:42–66`). Its `didReceive` is a no-op today (`:72`).
- Free-form event fires present the detail screen only when `event.photoFilename != nil`; its `didReceive` opens the detail screen for the Open action and a plain tap (`FreeFormEventFireHandler.swift:56–96`).
- `NotificationFacade` always completes with `[.banner, .list, .sound]` and stops consulting handlers after the first claim (`NotificationFacade.swift:35–40`, `:77–97`).
- The app already has an AVKit playback precedent: `FeedMediaPlayerSheet` uses one `VideoPlayer` sheet and starts playback on appear only because an explicit Play tap opened it — feed cards never autoplay (`FeedsView.swift:649–720`).

Binding properties:

1. **The reminder always fires, instruction or not.** A missing, corrupt, unsupported-codec, still-loading, or deleted video must never block, delay, or mute the reminder/notification. Presentation stays a side effect of delivery; any handler added for instructions must always return `false` and must not change the banner/list/sound outcome or the medication path.
2. **Fire-time presentation is extended, not replaced.** When an entry/event has an instruction, the fired screen shows the reminder content plus the instruction content: a text instruction renders as readable text at the user's size; an image instruction renders like today's photo aids; a video instruction adds an obvious, large affordance to play it. A media-only item must present; an item with no instruction keeps today's behaviour byte-for-byte. How media kinds share the fired screen is OD-4.
3. **Audio is user-initiated or clearly controllable — never an unexpected blast.** The default is an explicit Play control that opens full-screen playback (the `FeedMediaPlayerSheet` precedent). If autoplay is chosen, it must start muted with a visible unmute and be skippable; sound must never start merely because a reminder appeared. OD-4 records the exact choice.
4. **Elderly-first playback.** Large controls; standard AVKit transport available; no fine-motor precision; no swipe-only gestures; the play/pause surface and Close stay ≥44pt and reachable one-handed; VoiceOver labels for the video, caption, and each transport action; dynamic-type text for captions/titles. A tremor must not turn Play into a scrub.
5. **Failure is plain and non-blocking.** A missing/corrupt/unplayable video shows a short, localized, plain-language message (for example "This video is not available right now.") while the reminder's own title/time remain on screen; the screen can always be dismissed. Never a blank screen, a spinner that never ends, a raw error, or an error code in front of the user. The failure is logged PII-free (event type + outcome only).
6. **Foreground-only is the honest baseline.** Today the in-app fired screen exists only in the foreground (`willPresent`); a cold-launch/tap path for routines is explicitly later work (`RoutineVisualAidFireHandler.didReceive` no-op). v1 must either (a) implement the tap/Open path so the elder can reach the instruction after unlocking, or (b) state the limitation in the UI and the report — but it must not claim background video playback. Exact background/killed-at-fire behaviour is OD-6.
7. **No change to the notification taxonomy contract.** `NotificationCategories` is a full REPLACE builder; any new categories/actions must be added through it without dropping existing ones. Routine cancels remain scoped by identifier — never `removeAllPendingNotificationRequests` (`RoutineAlarmScheduler.swift:30–34`).

## Safety & Compliance Delta

**Safety delta: none.** This feature touches no safety-critical path: routine reminders and free-form events carry no acknowledgement window, escalation, or re-fire (`RoutineEntry.swift:77–80`), and medication reminders are explicitly out of scope. No new safety claim, alert, delivery guarantee, or biometric/PIN gate is added.

Rules that nonetheless bind:

- **Fail-safe degradation.** The video is a nicety; the reminder is the deliverable. Any media failure degrades to the reminder with a plain fallback — never to a failed or silent reminder (Fire-Time contract 1 and 5).
- **On-device only, no new egress.** Instruction video is never uploaded, transcribed, or AI-processed. Root Architecture Constraint 1 and the privacy standard bind unchanged; the recorded cloud exceptions (root OD-12, OD-13) do NOT apply. A YouTube link, if shipped, is the existing third-party YouTube integration category and must be labelled and failure-handled (OD-3).
- **Privacy of home video.** A video of a person exercising at home is personal data. It stays in app storage, is excluded from the Photos library and share sheets, is never named in logs, and dies with its reminder/event. The encrypted index (`RoutineEntry` / `EventExtras`) plus file protection is the at-rest story; no new data category leaves the device.
- **Permissions.** Point-of-use camera/microphone prompts with plain-language disclosure; denial is non-blocking (Capture contract 2).
- **Accessibility standards** bind as project standards: voice-first where a path exists, ≥44pt targets, ≥18pt body text, localised strings, plain language, owner copy rules.
- **No silent stubs.** If YouTube links, in-app recording, or background/cold-launch playback are not shipped, the UI must not present a control that claims them; deferred work explains itself explicitly (root Agent Principles).
- **Quality gate.** The project's 100% unit coverage + integration-test bar applies to safety-critical paths; this feature adds none. Its new code is still covered by scoped suites at the house standard, with the full-suite baseline unchanged (`ios/build.sh` is canonical; simulator-scoped `-only-testing` runs are the honest gate).

## Feature Constraints

1. **Root constraints bind unchanged.** On-device AI / no cloud LLM; PII-free logs; encrypted app storage where applicable; elderly-first accessibility; no silent stubs. This supplement adds no new safety-critical surface and claims none.
2. **Scope rule.** Two surfaces only: daily-routine reminders and app-created free-form events. Medication reminders, imported events, Android, and assistant voice authoring are out of scope.
3. **Storage rule.** Application Support video store with `.completeFileProtection`; bare file names in the encrypted model payload; delete with the owning entry/event; transactional replace; no video in the notification attachment store.
4. **Migration rule.** Optional fields with custom-decoder defaults; old payloads load; never lose a reminder list or event index to a missing key.
5. **Failure rule.** The reminder always fires. Missing/corrupt/unplayable video yields a plain, localized fallback and a PII-free log — never a block, a silent blank, or a raw error.
6. **Accessibility rule.** 44pt+/18pt+, no fine-motor precision, no swipe-only controls, VoiceOver labels, user-initiated or clearly controllable audio, localized copy.
7. **Notification rule.** Presentation handlers return `false`; banner/list/sound unchanged; medication alarms untouched; scoped cancels only; `NotificationCategories` full-REPLACE discipline respected.
8. **Permission rule.** Camera/microphone requested at point of use with plain-language `Info.plist` disclosure; denial non-blocking; library pick permission-free.
9. **Observability rule.** PII-free events only (no titles, captions, file names, or video content); the release-build log-surface gate (`ios/tools/check-release-log-safety.sh`, wired into `ios/build.sh`) must cover the new paths.
10. **Localisation rule.** All new strings en + ne in `Localizable.xcstrings`; spoken times (if any are spoken) only via the `SpokenTime` formatter.
11. **Delivery rule (house rule).** Task work runs ONLY in the dedicated worktree (sibling of the main checkout, branch `worktree-<slug>` / `feat/<slug>`), integrated via PR against master; never in the main checkout. Playback validation runs on a real device where a simulator cannot prove it.
12. **Test gate.** Focused/scoped XCTest suites per unit; extend the existing suites rather than inventing parallel ones: `RoutineEntryTests`, `RoutineSchedulerTests`, `RoutineStoreTests`, `VisualAidStoreTests`, `VisualAidDisplayStateTests`, `RoutineVisualAidFireHandlerTests`, `EventExtrasStoreTests`, `FreeFormEventServiceTests`, `FreeFormEventFormTests`, `FreeFormEventFireHandlerTests`, plus new playback / missing-file / failure-path tests behind an injectable seam (OD-7). `xcodebuild test` (not `build`) is the build-environment rule; `./build.sh` is canonical.

## Success Criteria & Completion Gate

1. A caregiver can attach, replace, and remove an instruction (text, image, or video) on a routine reminder and on a free-form event; a media-only item presents at fire time.
2. The elderly user can follow the instruction at fire time unaided: read text, view images, or play video with large controls and user-initiated or clearly controllable audio (confirmed success — OD-8).
3. Missing/corrupt/unplayable video: the reminder still fires and shows a plain, localized fallback; the failure is logged PII-free; no raw errors.
4. Storage/privacy: the video lives in the app store with file protection, is absent from Photos, is deleted with its owner, and never appears in logs.
5. No change to medication paths, notification banner/list/sound outcomes, read-aloud, or caregiver alerts.
6. Migration: pre-feature `RoutineEntry` and `EventExtras` payloads load unchanged.
7. Scoped new/extended suites green; typecheck/build clean; playback smoke-checked on a real device (simulator where honest).

## Decisions

All decisions below were resolved by the owner on 2026-10-25 ("go with your suggestions" on the proposed defaults, plus the media amendment). No open decisions remain; layout and implementation details belong to design-l1/l2.

1. **Media kinds (amendment).** RESOLVED: instructions cover **text, image, and video** (owner: "expand to original instruction to cover all medium"). One instruction per reminder/event in v1, of any single kind; video caps 3 minutes / ~200 MB stored as provided (no transcode); an unsupported codec is rejected at pick time with a plain message. Text instructions store as text in the encrypted payload; image instructions follow the existing photo-aid pattern; audio-only is out.
2. **In-app recording.** RESOLVED: ships in v1 (owner: "both"). System camera UI (`UIImagePickerController` or AVFoundation) with point-of-use camera + microphone prompts; `NSCameraUsageDescription` and `NSMicrophoneUsageDescription` amended; denial leaves library pick and the reminder fully working.
3. **YouTube links.** RESOLVED: not shipped in v1 (owner allows but does not recommend them). The model leaves room for a later `link` instruction kind (URL stored, not bytes, played through the existing YouTube integration with honest offline/failure handling).
4. **Fire-time playback UX, autoplay, and composition.** RESOLVED: the fired screen shows the reminder text plus the instruction content for its kind (text renders as readable text, images as today's photo aids, video as a large Play control); Play opens full-screen AVKit `VideoPlayer`; no sound before an explicit action; an item with both photos and a video shows the photos as today plus the video Play affordance (order TBD by design).
5. **Storage location, file format, Data Protection class.** RESOLVED: dedicated `Application Support/InstructionVideos/<entryId>/` for routines and a separate event root (not mixed into `VisualAids` / `EventPhotos`), bare filenames in the encrypted payloads, `.completeFileProtection` (the photo-aid class), receive-as-is file format (no on-device transcode). Playback only occurs while the app is foreground/unlocked, so complete file protection is acceptable.
6. **Backgrounded / killed-at-fire-time behaviour.** RESOLVED: v1 keeps foreground presentation; the routine tap-to-open path IS in v1 scope (owner's brief: tapping the notification takes the user to the instructions), so a banner tap / Open action opens the reminder/event with the instruction playable after unlock; no background video claim. No extra notification action button ("Watch video") — keep the surface simple.
7. **Test strategy for AVFoundation playback.** RESOLVED: a thin injectable playback seam (protocol in the `CameraCapturePresenting` style) so unit tests script play/pause/failure/missing-file outcomes without a player, plus one real-device smoke check for rendering and audio; simulator tests cover every failure path. No UI test required.
8. **Success criteria.** RESOLVED: success = a caregiver can attach an instruction (text, image, or video) to a routine reminder or free-form event, and when the reminder fires the elderly user can follow it in the app unaided.
