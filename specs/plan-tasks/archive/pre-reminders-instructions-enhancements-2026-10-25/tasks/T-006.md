## Description
Resolve review-l2 R-2. Hoist the challenge-timeout constant to **one named home**: `ConfirmationChallenge.defaultChallengeTimeoutSeconds` (the initializer default at `ConfirmationChallenge.swift` :21/:28–33 becomes a reference to that static; the value is used at :43 as today). `MedicationScheduler` gains a stored `challengeTimeoutSeconds` with an initializer parameter defaulting to the named home, and **passes it explicitly** at both construction sites — the first-call-issues challenge (`MedicationScheduler.swift` :255) and `startConfirmationChallenge` (:434). Create `AckClarificationConfig` (the walk's window type, used by T-013 in W2) whose `responseWindowSeconds` derives from the same named home. No literal timeout at any call site. Keep the existing shorter-window injection test and extend it.

## Acceptance criteria

```gherkin
Feature: One configured challenge window, no literal at any call site

  Scenario: Both challenge construction sites honor the single configured value
    Given MedicationScheduler is constructed with challengeTimeoutSeconds defaulting to ConfirmationChallenge.defaultChallengeTimeoutSeconds
    When the first-call-issues path (:255) and the startConfirmationChallenge path (:434) construct their ConfirmationChallenge
    Then each construction passes the configured value explicitly
    And the issued deadline is now plus that value for both paths

  Scenario: A shorter injected window is honored (edge)
    Given a scheduler constructed with a shorter challengeTimeoutSeconds
    When a challenge is issued and its window elapses unanswered
    Then the timeout path re-enters escalation on the shorter window
    And the default value is not read anywhere in that path
```

Concrete checks: a repository search for a literal timeout value (numeric) at any `ConfirmationChallenge(` or `AckClarificationConfig(` call site returns none; `AckClarificationConfig().responseWindowSeconds == ConfirmationChallenge.defaultChallengeTimeoutSeconds`.
