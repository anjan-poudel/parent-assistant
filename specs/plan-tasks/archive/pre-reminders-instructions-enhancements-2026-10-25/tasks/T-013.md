## Description
Add the coordinator's walk seams. `medicationAckCandidates()` is a pure in-memory read (IF-7) returning the pending reminders' candidates with canonical names in the fixed order scheduledAt, canonical name, id. The walk state (walk rides the shipped `isAwaitingConfirmation` OR-fold, `AppCoordinator.swift` :12916) exposes `beginAckClarification(candidates:)`, `ackClarificationResponse(utterance:) -> AckClarifyOutcome` and `endAckClarification(reason:)` with reasons resolved / denied / expired; the response window comes from `AckClarificationConfig` (T-006, W0 — never a literal); state is main-confined. Semantics: pair form first (cursor 0, the resolver's two candidates); `yes` falls to the single form at cursor 0; `no` ends the walk; **three or more candidates: `no` advances the cursor and asks the next candidate; after the last candidate's `no` the walk ends** (m-4) with nothing recorded. The walk never records anything itself; on `resolved` the caller continues the shipped safety sequence.

## Acceptance criteria

```gherkin
Feature: Conservative disambiguation with the sanctioned copy

  Scenario: An ambiguous utterance prompts the sanctioned clarification
    Given the morning slot has pending reminders for "Amlodipine" and "Metformin"
    When the elder's utterance does not identify a single medication
    Then the clarification asks in the sanctioned did-you-mean form
    And on the elder's affirmative answer the named entry resolves and continues the safety sequence

  Scenario: The same ambiguity always produces the same clarification
    Given the same ambiguous utterance and the same pending set
    When the utterance is processed twice
    Then the same clarification is produced both times

  Scenario: Three or more candidates advance on no and end after the last no (edge)
    Given pending candidates A, B and C in the fixed order
    When the elder answers no twice and yes once
    Then the walk resolves to C
    When the elder instead answers no three times
    Then the walk ends with nothing recorded

  Scenario: An unresolved utterance records nothing (failure)
    Given an ambiguous utterance
    When the elder does not resolve the clarification
    Then no dose is recorded
    And no medication was chosen by guessing, recency or firing order
```

Concrete checks: candidate order is always scheduledAt, canonical name, id (never firing order); the window default equals `ConfirmationChallenge.defaultChallengeTimeoutSeconds`; an expired window ends the walk with the honest ended line and records nothing.

## Implementation notes
- Walk lifecycle only; the router interception and the utterance plumbing are T-014 (W3), which depends on this unit.
- Nothing is persisted by the walk; a resolved walk hands the entry to the shipped acknowledgement chain.
- Denial handling is not here: `no` is a walk end, and the router-level denial falls through to the refusal ladder (T-014).
- No LLM symbols; no new vocabulary (the resolver's tables and the shipped ack lists are the only vocabulary).
