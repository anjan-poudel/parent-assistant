# T-016: Fire handlers — instruction-aware presentation and three tap cases

## Description
Make a routine reminder present the fired screen when it has a photo or an instruction, carry the notification's `had_instruction` and delivery date as a typed context, and route a tap through three explicit cases: instruction present, instruction removed, and owner deleted. A photo-only or pre-upgrade tap stays a no-op. Both handlers always return false, so the notification facade and the caregiver path are never muted.

## Acceptance criteria

```gherkin
Feature: Instruction-aware fire handlers

  Scenario: Foreground delivery presents when either a photo or an instruction exists
    Given a routine reminder with had_instruction true and an entry with an instruction
    When willPresent runs
    Then onFire receives the entry and a context with hadInstruction true and the delivery date
    And the handler returns false
    Given an entry with neither a photo nor an instruction and had_instruction false
    When willPresent runs
    Then onFire is not called
    And the handler returns false

  Scenario: A tap with an instruction opens the instruction screen
    Given had_instruction true, an entry that exists, and an instruction present
    When the default action is received
    Then onInstructionTap receives the entry id, the entry and the delivery date once

  Scenario: A tap after the instruction was removed still presents the fallback
    Given had_instruction true, an entry that exists, and no instruction now
    When the default action is received
    Then onInstructionTap receives the entry once
    And the removed state is rendered by the surface

  Scenario: A tap after the owner was deleted presents a notice, never a dead tap
    Given had_instruction true and the entry lookup returns nil
    When the default action is received
    Then onInstructionTap receives the id, nil and the delivery date once
    And the surface can render instruction.reminderUnavailable with Close

  Scenario: A photo-only or pre-upgrade tap does nothing
    Given had_instruction is false or the key is absent
    When the default action is received
    Then onInstructionTap is not called
    And the system still handles the tap

  Scenario: An event presents when it has a photo or an instruction
    Given a free-form event with an instruction and no photo
    When willPresent runs
    Then the event presentation sink is called
    And the handler returns false
```

## Implementation notes
- Follow design §2.14 (C14), §3.6 (IF-31 and `RoutineInstructionFireContext`), §4.11 (tap context), §11.3 B (three tap cases), §11.3 S (always false).
- **B-1 (review-l1):** the tap sink takes an **optional** entry: `onInstructionTap(entryId: UUID, entry: RoutineEntry?, firedAt: Date)`. A deleted owner reaches the `.unavailable` notice; it is never silently dropped and never renders a dead screen.
- `RoutineInstructionFireContext` is a small `Equatable` struct declared beside the handler, carrying `hadInstruction` and `firedAt`. `had_instruction` is read from `userInfo`; absent reads false.
- **FR-RIE-016:** both handlers return false on every path, including their didReceive. Add explicit assertions; this is a safety rule for read-aloud and caregiver delivery.
- The routine foreground gate is `!entry.visualAids.isEmpty || entry.instruction?.isPresent == true || context.hadInstruction`. The event gate is `event.photoFilename != nil || event.instruction?.isPresent == true`.
- Only the default action opens the instruction screen. Other actions are ignored. Do not add categories, actions, acknowledgement or escalation.
- No instruction text, caption, filename or URL enters any payload or log.
- Do not edit `NotificationFacade.swift`, `NotificationCategories.swift` or the coordinator registration; T-025 wires the new sinks.
