## Description
Wire the significant-event triggers and the two event hooks.
**Triggers.** `intakeRecorded` fires after the adherence-log write succeeds in `finalizeAcknowledgement` (never on a persist failure — the alert follows the write, the shipped order); `escalationStarted` fires at the first re-fire decision — the `.fireReminder(let refireCount)` arm (:394) where `refireCount` goes 0→1 (`EscalationEngine.swift` :117, `.fireReminder` at :146) — exactly once per reminder, with no stored flag (D10). `missedMedication` (`recordMissedDose` :551) and `possibleDoubleDose` (the blocked branch of `checkDoubleDoseAndRecord`, :511–538) now carry their `context`; the first-fire notification stays **opt-in exactly as shipped** (:353 is not touched). All significant-event triggers are unconditional (the four types above are not toggle-gated).
**Hooks.** `onSignificantEvent` is invoked at the three at-risk sites (missed dose; blocked double-dose branch; first re-fire decision); `onSlotEntryRetimeRefused` fires on a refused retime.
**Retime refusal (m-5).** `setScheduleTimes` (:152) refuses for slot entries (`slot != nil`): no change is applied, the named PII-free event `medication_retime_refused` is emitted (metadata `entry_id_hash` and `slot` only), and the `onSlotEntryRetimeRefused` hook fires for the one-shot settings note (wired in T-020). Legacy entries keep the shipped behavior. Escalation semantics are preserved untouched (FR-MSR-019): same Date arithmetic; a future dose stays future.

## Acceptance criteria

```gherkin
Feature: Significant events fire exactly once, and slot retimes refuse honestly

  Scenario: The first re-fire announces escalation started
    Given an outstanding reminder whose acknowledgement window expired
    When the scheduler takes its first re-fire decision (refireCount 0 to 1)
    Then the escalationStarted significant event is emitted once
    And a later re-fire does not emit it again

  Scenario: Intake recorded follows the written record
    Given the elder completed the confirmation challenge
    When the adherence log write succeeds
    Then the intakeRecorded significant event follows the write
    And when the write fails, intakeRecorded is not emitted

  Scenario: The first-fire gate stays opt-in (guard)
    Given a household that has not enabled first-fire notifications
    When a reminder fires for the first time
    Then no first-fire significant-event notification is sent
    And the shifted behaviour is exactly the shipped one

  Scenario: A slot entry's retime is refused and surfaced (edge)
    Given a slot entry
    When setScheduleTimes is called for it
    Then no change is applied
    And medication_retime_refused is emitted with the entry id hash and slot only
    And the refusal hook fires
    And a legacy entry's setScheduleTimes still applies as shipped
```
