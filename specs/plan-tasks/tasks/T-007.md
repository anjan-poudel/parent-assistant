## Description
Create the on-device evidence store: `store(image:for logId:entryId:) -> Result<String, EvidenceStoreError>` compressing an image under the named cap constant (the PhotoVerifier precedent value `200 * 1024` reused as a constant — the store does not call, wire or repurpose PhotoVerifier), writing atomically under `Application Support/MedicationEvidence/<entryId>/`, with same-name writes replacing in place; `delete(fileName:entryId:)` fail-soft (absent = success); `deleteAll(for entryId:)` a fail-soft Void cascade for the remove path (T-017); `fileURL(for:fileName:entryId:)`. Errors are the typed D8 set: `compressionFailed` / `storageUnavailable` / `removeFailed` (the L1 outline case is replaced, not realized — N-1). Nothing in this component touches the network.

## Acceptance criteria

```gherkin
Feature: Medication evidence stays on-device and fails honestly

  Scenario: A capture round-trips through the store
    Given an image under the compression cap
    When it is stored for a log id and entry id
    Then the returned bare file name reads back to the stored image
    And a repeated store under the same name replaces in place

  Scenario: An incompressible image fails typed and persists nothing (failure)
    Given an image that cannot compress under the cap
    When it is stored
    Then the result is a compressionFailed error
    And nothing is persisted

  Scenario: Deleting what is absent is a success (edge)
    Given an entry directory with no such file
    When the file is deleted
    Then the delete succeeds (absent = success)
```

## Implementation notes
- The cap constant reuses the PhotoVerifier precedent value; PhotoVerifier itself is not referenced, called or changed (FR-MSR-020 keeps the dementia machinery untouched).
- Failed compression deletes any partial output (no orphan files).
- No PII in any error surface; no photo content in logs.
- Store work is synchronous here; the off-main orchestration and single-flight discipline belong to the capture plumbing (T-021).
