## Description
Wrap camera and microphone authorization behind one `Sendable` protocol with a five-case status that includes restricted. The capture coordinator consults this seam and never calls AVFoundation authorization directly. Requesting is explicit; reading status never prompts.

## Acceptance criteria

```gherkin
Feature: Instruction capture permissions

  Scenario: Status reads never prompt
    Given the person has never seen a camera prompt
    When the coordinator reads camera status
    Then the returned status is notDetermined
    And no system prompt is shown

  Scenario: Every platform status maps to one of five values
    Given the platform reports authorized, denied, restricted, notDetermined or an unknown value
    When status is mapped
    Then the result is authorized, denied, restricted, notDetermined or restricted respectively
    And no case is dropped or collapsed

  Scenario: A denied camera is a plain problem, not a crash or a loop
    Given camera authorization is denied or restricted
    When the coordinator requests camera access
    Then the result is a permissionProblem with the matching case
    And the microphone is not requested after the camera denial
    And no recording begins

  Scenario Outline: Microphone is requested only after the camera is usable
    Given camera status is <camera>
    When recording preparation runs
    Then the microphone request count is <micRequests>

    Examples:
      | camera        | micRequests |
      | authorized    | 1           |
      | notDetermined | 1           |
      | denied        | 0           |
      | restricted    | 0           |
```

## Implementation notes
- Follow design §2.6 (C05), §3.5 (five-case status), §10.1 (exact Info.plist text is T-020's concern, not this file), §11.3 R (permission order).
- **M-1:** the order is camera first, microphone only after the camera is usable. A camera denial or restriction short-circuits and never prompts for the microphone. T-009 verifies the order at the coordinator; this unit provides the primitives and its own ordering test.
- The protocol is `Sendable`; the production adapter is a value type or a stateless final class with no shared mutable state.
- `restricted` is a real case, not denied. The copy differs (T-007 owns the mapping).
- Do not add Settings deep links, "open Settings" buttons or retry loops. FR-024 forbids claiming a path the app cannot open here; the plain problem line is the whole response.
- Do not touch `Info.plist` or `project.yml`; T-020 owns the usage disclosure and built-bundle registration.
