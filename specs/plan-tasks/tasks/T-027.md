## Acceptance criteria

```gherkin
Feature: Instruction feature integration and release gates

  Scenario: A routine instruction survives the full path
    Given a routine entry with a text, image or video instruction created through the real seams
    When the app arms, fires and presents the reminder
    Then the reminder fires whether or not the instruction exists
    And the notification payload carries only had_instruction
    And a tap with the instruction present opens the instruction card
    And a tap after the instruction is removed shows the removed fallback with the fire time
    And a tap after the owner is deleted shows the unavailable notice with Close

  Scenario: Legacy payloads from every prior shape still load
    Given the F-1 through F-12 migration fixtures, including a pre-instruction routine, a pre-instruction event, a text instruction, an image instruction and a video instruction
    When the stores decode them
    Then every fixture loads without throwing
    And no instruction media is deleted during the load
    And the medication and visual-aid payloads are untouched

  Scenario: The medication path and notification taxonomy are unchanged
    Given the medication scheduling and notification category suites
    When they run
    Then they pass exactly as on the baseline
    And no medication identifier, category, action or timer was added or removed
    And the routine scoped cancels remain scoped

  Scenario: The full suite has zero new failures
    Given the documented full-suite baseline for the starting commit
    When the single post-change full-suite run completes
    Then every baseline failure is still the same failure
    And there are zero new failures
    And every new instruction suite passes

  Scenario: The gate and the canonical build pass
    Given the release-log gate and the canonical build
    When both run on the final tree
    Then the gate exits clean
    And the build produces an installable app
    And no security setting or allow-list entry was weakened

  Scenario: The device smoke is recorded honestly
    Given a Release build and the 14-step device smoke checklist
    When the checklist is executed on the owner's device
    Then each step is recorded pass or fail with evidence
    Or, when no device is available, the whole checklist is recorded as an outstanding gate with the exact reason
    And no step is claimed as passed without evidence

  Scenario: The AI and voice pipeline cannot break reminder delivery
    Given the app with the AI, voice and LLM components unavailable or crashed
    When a routine reminder fires
    Then notification delivery and the fired screen still work
    And no instruction path calls into those components
```

## Implementation notes
- **One full-suite run:** do not run the full suite per unit or per wave. Waves use the scoped filters in `plan.md`; this unit performs the single full-suite comparison at the end.
- **Baseline:** the coordinator records the full-suite result on the starting commit in the run notes before wave 0. This unit compares pass/fail sets against that record and reports zero new failures. If the baseline record is missing, record the run as inconclusive rather than claiming green.
- **Worktree hazards:** symlink `whisper-medium-ne-q5_1.bin` and the kws assets from the main checkout before building; prune stale worktree DerivedData (about 4.5 GB per worktree) to avoid a silent ENOSPC failure. Use `xcodebuild test`, not `xcodebuild build`; `./build.sh` is the canonical build.
- **Device smoke:** the checklist needs the owner's device. If it is unavailable in this run, record the gate as outstanding with the exact step list and reason. Do not mark it passed from a simulator run.
- **NFR-RIE-008:** record the measured preflight, first-frame and failure-fallback timings if the smoke is executed; otherwise mark timing evidence outstanding.
- **Scope boundary checks:** no links or URL playback, no transcode/compression/trimming, no cloud or new egress, no instruction notification category/action/attachment, no medication-path change, no multi-instruction, no photo-library access, no Settings deep link, no audio captioning, no `SpokenTime`.
- This unit may add temporary verification scripts only inside `specs/plan-tasks/`; do not add product code.
- The final commit/PR uses the house process. Do not merge as part of this unit unless the workflow's review stage authorises it.
