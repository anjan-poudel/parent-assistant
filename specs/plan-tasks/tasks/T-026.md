# T-026: Release-log gate registration and source-hygiene suite

## Metadata
- **Group:** TG-07 — Gates and release

## Owned files
- Extends `ios/tools/check-release-log-safety.py` with the feature roots and event types.
- Creates `ios/ElderlyAssistantTests/Services/Instructions/InstructionSourceHygieneTests.swift`.

## Description
Register the feature with the build-blocking release-log gate and add the source-hygiene suite that proves the scope boundary: no new egress, no photo-library access, no `copyItem` in the staging path, no share or export path, and no free-text logging from the new files. The gate must fail on a planted violation, not merely pass on today's tree.

## Acceptance criteria

```gherkin
Feature: Instruction source hygiene and release-log gate

  Scenario: The gate scans the feature roots
    Given the release-log script's feature roots
    When the gate runs
    Then Services/Instructions, App/InstructionViews.swift and App/InstructionCapture.swift are scanned
    And every new file under those roots is covered
    And RoutineNotificationContent.swift is not declared a root because it writes no log

  Scenario: The gate recognises the new event types
    Given the script's event-type register
    When the instruction event names are inspected
    Then all seven catalogue names are recognised
    And no allow-list entry was removed
    And an unknown event name in a feature file fails the gate

  Scenario: A planted free-text log fails the gate
    Given a temporary copy of a feature file with an interpolated instruction text in a log call
    When the gate runs on that copy
    Then it exits non-zero and names the file and pattern
    And the shipping tree is not modified

  Scenario: Source hygiene proves the scope boundary
    Given the feature sources
    When the hygiene suite scans them
    Then there is no URLSession, network client, upload or share call
    Then there is no Photos or photo-library access
    Then there is no copyItem in the video store path
    Then there is no transcode, compression or trimming API
    And there is no Bundle.main.object(forInfoDictionaryKey:) use for the usage descriptions

  Scenario: The gate remains honest about its limits
    Given the script's documentation
    When the limits are read
    Then it states that dynamic or indirect logging is not proven
    And the test suite does not claim more than the scan proves
```

## Implementation notes
- Follow design §6.3 (release-log gate additions and honest limits), §8.3 (threat model), §11.3 P (source hygiene), §11.3 N.
- Add exactly these roots: `ios/ElderlyAssistant/Services/Instructions` (directory), `ios/ElderlyAssistant/App/InstructionViews.swift` and `ios/ElderlyAssistant/App/InstructionCapture.swift`. Add the seven event names to the feature event types: `instruction_media_import`, `instruction_media_delete`, `instruction_media_availability`, `instruction_playback`, `instruction_image_load`, `instruction_capture_permission`, `instruction_orphan_purge`.
- Do not remove or weaken any existing allow-list entry. `RoutineNotificationContent.swift` is deliberately not a root: it lives in a shared directory, writes no log and carries two producer keys plus a Bool.
- The self-test must operate on a temporary copy and prove the gate fails a planted violation. It must not edit the shipping tree, and it must clean up.
- The hygiene suite complements the gate; it does not replace it. Keep the gate build-blocking.
- No change to security settings, CI permissions or the script's failure convention.
- `ios/tools/check-release-log-safety.py` is a Python file, but the plan and tests must not embed a Python code fence. Cite it as a path only.
