## Description
Build the shared instruction surfaces: one card that renders every display state, one full-screen cover that hosts playback, and one editor used by both the routine and event flows for text, image and video. The views receive values and action closures; they never reach a store, a service or a coordinator. Honesty is the point: nothing claims a control that cannot work.

## Acceptance criteria

```gherkin
Feature: Instruction surfaces

  Scenario Outline: The card renders each display state without inventing content
    Given a display state <state>
    When the card renders
    Then it shows <surface>
    And it does not show a control the state cannot support

    Examples:
      | state            | surface                        |
      | none             | nothing at all                 |
      | text             | the text, full width           |
      | image            | the photo and optional caption |
      | video            | a play control and caption     |
      | unsupported      | any saved text plus one note   |
      | removed          | one removed line               |

  Scenario: The play control is 44 points and playback requires a tap
    Given a video instruction
    When the card appears
    Then the play control meets the 44 point floor
    And no player is created until the control is activated

  Scenario: A load or playback failure shows one plain line
    Given an image that cannot load or a video that cannot play
    When the surface renders
    Then one plain unavailable line appears
    And no error code, filename, path or technical detail is shown

  Scenario: The editor saves text, image or video with an optional caption
    Given the editor opened for a text, image or video instruction
    When the person saves
    Then the save action receives one resolved draft
    And a media draft without pending bytes cannot be saved
    And removing the instruction is an explicit choice

  Scenario: The editor uses the capture coordinator and never a photo library
    Given the person chooses to record a video
    When the recorder path runs
    Then the editor delegates to the capture coordinator
    And no PHPicker photo mode is used
    And no permission is requested by the view

  Scenario: Every visible string is localised and accessible
    Given the card, cover and editor
    When their source is inspected
    Then no elder-facing English literal is present
    And every key used exists in both languages
    And the image and video accessibility labels match the design
    And the surfaces support Dynamic Type without clipping
```

## Implementation notes
- Follow design §2.9 (C08), §4.9–§4.10 (display state to surface), §10.2–§10.3 (accessibility and copy), §11.3 O (accessibility pins), §11.3 Q (honest capability surface).
- `.none` renders `EmptyView` — nothing, not an empty container with padding. `.removed` is a line, not a dead control. `.unsupported` never produces a play button or a link.
- The editor is shared by both flows. Inject a save closure that takes a `InstructionCommit`; do not inject `AppCoordinator`, `RoutineScheduler` or `FreeFormEventService`. Views never reach a store.
- Video capture is delegated to `InstructionVideoCaptureCoordinator`; the editor observes its state and consumes an accepted video exactly once. No player starts from the editor.
- Use `L10n.str` and `L10n.fmt` only. `instruction.atTimeFormat` uses the formatter path. No English literals in elder-facing positions.
- Image accessibility is "Instruction photo"; video accessibility is "Instruction video. Play". Captions are their own text. Dynamic Type uses flexible layouts, not fixed heights.
- Do not add a photo-library picker, Settings deep link, YouTube/link playback, URL field, share sheet, transcode or trimming control.
- `InstructionSurfaceTests` is a source-pin and value suite in the house style; T-021 later extends it for the fired screen.
