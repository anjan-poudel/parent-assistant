## Description
Rebuild the medication editor form (`MedicationScheduleSettingsView`, :4494) around the slot model. Controls: slot picker (morning / afternoon / evening), quantity value plus unit, before/after-meal relation, an add-another-dose row producing one draft row per dose, and the med row (`medRow`, :4576) rendering each entry's slot and meal context. Scan-to-fill stays wired to the draft (T-009) with the shipped additive rules — correction happens in the form, binding only at save (FR-MSR-006). Edit-existing flow: tapping a row opens the form prefilled — legacy entries preselect the clock model exactly as stored (exact-equality, no fuzzy match), switching an existing entry to the slot model is an explicit family choice (no silent conversion), and a slot entry reopens in slot mode. The purpose step is untouched (FR-MSR-004). All interactive elements meet the elderly-fit floor: 44pt minimum targets and 18pt minimum type (NFR-MSR-005, FR-MSR-021). Save calls IF-21; the family is never asked for a clock time in slot mode.

## Acceptance criteria

```gherkin
Feature: The family edits doses by what, how much, when in the day and before or after meals

  Scenario: Family saves an entry in the new model
    Given the medication editor for a household
    When the family enters a medication name, a quantity, the morning slot and the before-meal relation and saves
    Then the entry is persisted with its quantity, slot and meal relation
    And the family was never required to enter a clock time

  Scenario: Editing a legacy entry preselects the clock model exactly (edge)
    Given an existing legacy entry with stored times
    When its row opens the editor
    Then the clock model is preselected
    And the stored times are shown exactly as stored
    And no silent conversion to the slot model happens

  Scenario: The controls meet the elderly-fit floor (guard)
    Given the rebuilt editor form
    When its interactive elements are measured
    Then each has at least a 44pt interaction target
    And user-visible type is at least 18pt

  Scenario: An empty scan read changes nothing (failure)
    Given the form with values entered
    When a scan returns an empty read
    Then no form value changes
    And nothing binds before save
```
