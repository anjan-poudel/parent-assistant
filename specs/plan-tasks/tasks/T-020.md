- Creates `ios/ElderlyAssistant/Resources/ne.lproj/InfoPlist.strings`.

## Description
Declare camera and microphone use in plain language and ship both localisations as real `InfoPlist.strings` resources. The test must inspect the built bundle's `en.lproj` and `ne.lproj` files directly: reading `Bundle.main.object(forInfoDictionaryKey:)` proves only the merge result and cannot catch a missing or malformed strings file. This unit is the sole owner of must-carry finding **M-3**.

## Acceptance criteria

```gherkin
Feature: Capture usage disclosure

  Scenario: The Info.plist declares exactly the two new usages in English
    Given the app Info.plist
    When its usage-description keys are inspected
    Then NSCameraUsageDescription and NSMicrophoneUsageDescription are present
    And their English values match the design text exactly
    And no photo-library, location or other new usage key was added
    And the existing contact-related usage key is unchanged

  Scenario: Both localisations exist as parseable strings files in the built bundle
    Given a built app bundle
    When en.lproj/InfoPlist.strings and ne.lproj/InfoPlist.strings are inspected
    Then both files exist
    And both parse as property lists
    And each contains both usage keys
    And the English file matches the Info.plist English values
    And the Nepali file contains the exact Devanagari copy

  Scenario: The test never trusts the merged Info dictionary
    Given the built-bundle assertions
    When their source is inspected
    Then they open the .strings files directly
    And they do not call Bundle.main.object(forInfoDictionaryKey:) for these keys

  Scenario: Removing one localisation fails the gate
    Given a bundle with ne.lproj/InfoPlist.strings deleted
    When the gate runs
    Then it fails naming the missing file
    And it does not fall back to English silently
```

## Implementation notes
- **M-3 (review-l2 Condition):** assert on the **built bundle**: `Bundle.main.bundleURL.appendingPathComponent("en.lproj/InfoPlist.strings")` and the `ne.lproj` twin, or an equivalent URL resolved from the test host. Read and parse those files (for example with `PropertyListSerialization`), then compare values. Never use `Bundle.main.object(forInfoDictionaryKey:)` for these assertions; it cannot distinguish a missing localisation from a merged one.
- The English `Info.plist` values and the `en.lproj/InfoPlist.strings` values must be byte-identical strings. The Nepali file carries the exact Devanagari copy from the design. The current tree has `Base.lproj` only, so the two directories are new.
- `ios/project.yml` needs explicit entries for both `InfoPlist.strings` files. The existing `Localizable.xcstrings` entry documents why a single-file resource must be declared; follow that pattern. Do not add the strings files as sources.
- Extend the existing `testThePlistAddsNoNewUsageDescriptionKeys` (or its equivalent) so exactly the two new keys are allowed; do not delete the guard. There is no photo-library key and must not be one.
- The build must be a Release-built bundle for the device-smoke evidence, but the test may run against the Debug test host as long as the resource-copy phase is the same. Record which bundle was inspected in the test comment.
- Do not touch the copy catalogue (`Localizable.xcstrings`) in this unit; T-019 owns it and this unit is its successor in a later wave.
