## Description
Teach the free-form event flow to carry one instruction through the same transactional seam as a routine. Saving an event is unchanged when no instruction is involved; when one is, the event save happens first and the instruction is written second, with a partial outcome that the surface can report honestly. Deleting or editing an event tears down or replaces its instruction media.

## Acceptance criteria

```gherkin
Feature: Free-form event instructions

  Scenario: Saving an event without an instruction is unchanged
    Given a valid event form with no instruction draft
    When save runs
    Then the event is saved exactly as today
    And no instruction media is written
    And no extras row is created unless a photo or instruction exists

  Scenario: Saving an event and its instruction reports partial success honestly
    Given a valid event form with a validated instruction video
    When the event saves but the instruction write fails
    Then the outcome is instructionSaved with the event saved
    And the event remains visible and editable
    And no media is orphaned

  Scenario: The instruction transaction is ordered for events too
    Given an existing event with an instruction video and a replacement pending video
    When setInstruction runs
    Then the new bytes commit before the extras row names the file
    And the extras row persists before the old file is deleted
    And event_instruction_updated is emitted once on a real change

  Scenario: A missing event row changes nothing
    Given an event id no longer present in the extras index
    When setInstruction runs
    Then it returns failure ownerNotFound
    And no bytes are written or deleted

  Scenario: Deleting an event deletes its instruction media
    Given an event with an instruction video
    When the event is deleted
    Then the extras row is removed
    And deleteAll for that event owner is attempted
    And a delete failure does not fail the event deletion

  Scenario: A write failure keeps the previous instruction and its file
    Given an event with an existing instruction and a media commit that fails
    When setInstruction runs
    Then it returns failure mediaWriteFailed with the storage cause
    And the extras row still names the previous file
    And the previous file still exists
```

## Implementation notes
- **Implementation pin P-1:** `FreeFormEventDraft.swift` does not exist in this worktree. `FreeFormEventForm` is declared in `ios/ElderlyAssistant/Services/Events/FreeFormEventService.swift` (line 97 at plan time). Extend that file; do not create the phantom file or cite it in any ownership list.
- Follow design §2.12 (C13), §3.6 (IF-24/IF-25), §4.5 (extras and form deltas), §5.6 (ordered transaction), §11.3 F/G.
- `save(_:editing:) -> FreeFormEventSaveOutcome?` returns nil when the event itself was not saved. A saved event with a failed instruction returns the partial outcome named by the design (`instructionSaved` holds the event and the instruction error). Do not report total failure for a saved event.
- **OI-1 translation:** `EventExtrasStore.setInstruction` returns `Bool`; this service maps `false` to `InstructionWriteError.persistenceFailed` at its own seam. Do not leak the `Bool` to the view.
- Event instruction media uses the event owner root (`ev-<sha256>`), never the routine root. Delete uses `deleteAll(for:)` for that owner.
- Event notifications gain no `had_instruction` key (design OI-8). The event tap already opens the detail; absence renders `.none`.
- Keep the existing event-title, address, recurrence and photo behaviour unchanged. Do not add transcode, trimming, upload, sharing or a second event store.
- `FreeFormEventService.swift` is a shared hotspot; this unit is its only owner in the plan.
