## Description
Settings → Medications first shows the family's existing schedules. The new
`MedicationManageListView` renders one row per `coordinator.medicationEntries`
entry — name, the composed dose line (`DoseLine.compose`), the slot + meal
context, and the purpose caption (`MedicationPurpose.label`) — with an explicit
add control (`settings.meds.add`). Tapping a row opens the existing editor
PRE-FILLED through the shipped T-018 conversion flow (the `draft(from:)` statics
and `editingEntryId` in `MedicationScheduleSettingsView`) — reuse, never rebuild.
The add control opens the same editor in new-entry mode. **The add form never
auto-opens**: the manage list is the screen; the editor is reached only by an
explicit tap. Empty state reuses `settings.meds.empty`. Legacy entries (clock
model) list and edit exactly as stored — no silent conversion (T-018's pin
stands). The Medicine-times card and its one-shot retime note (T-020) remain
reachable on the manage screen. Voice-first flows are untouched. All interactive
elements keep the elderly-fit floor: 44pt minimum targets, 18pt minimum
user-visible type (NFR-MSR-005, FR-MSR-021).

## Acceptance criteria

```gherkin
Feature: Settings shows the family's medication schedules first, not a blank form

  Scenario: The list renders every existing schedule
    Given a household with existing medication schedules, including legacy entries
    When the family opens Settings and then Medications
    Then every schedule is listed with its name, dose line, slot and meal context, and purpose caption
    And legacy entries appear exactly as stored
    And the add form is not open

  Scenario: Tapping a row opens the editor pre-filled
    Given the manage list with an existing schedule
    When the family taps that schedule's row
    Then the editor opens filled from that entry
    And saving edits the same entry (no duplicate is created)

  Scenario: The add control opens a new-entry form
    Given the manage list
    When the family taps the add control
    Then the editor opens in new-entry mode
    And the empty form is not what Settings showed on arrival

  Scenario: A household with no schedules sees the honest empty state
    Given a household with no medication schedules
    When the family opens Settings and then Medications
    Then the existing empty message "No medications scheduled yet" is shown
    And the add form is not open until the add control is tapped

  Scenario: The controls meet the elderly-fit floor (guard)
    Given the manage list's interactive elements
    When they are measured
    Then each has at least a 44pt interaction target
    And user-visible type is at least 18pt

  Scenario: A saved medication appears immediately and survives relaunch
    Given the family saves a medication schedule
    When the save completes
    Then the new row is visible in the manage list without relaunch
    And after a process kill and relaunch the row is still visible
    And its reminder has been re-armed from the persisted entry

  Scenario: A failed persist is loud and never silently accepted (failure)
    Given a storage write failure on the medication entries key
    When the family saves a medication schedule
    Then the save surfaces failure honestly (no reset-form success implied)
    And the entries event carries the shipped persistence-failure event
    And no reminder is armed behind a schedule that was not persisted
```

## Implementation notes
- **Persist tail (owner report 2):** `loadSchedule`'s write result is discarded (`_ = storage.write(key: "medication.entries", …)`, MedicationScheduler.swift :367 in the post-W6 tree) while its callers (:12147, :12326, :12463, :14394 in AppCoordinator; :323 `setScheduleTimes`) treat it as success. A failed write therefore surfaces as "saved" while nothing is persisted — the real-loss path behind "it just disappeared". Fix mirrors the shipped checked writes (:266 `setVisualAids`, :548 re-arm path): check the result, emit the shipped `entry_persistence_failed` (PII-free), make the failure caller-visible (honest failure to the view), and honor FR-MSR-022/D2 — persist first; on failure nothing is adopted/armed behind an unpersisted schedule. `MedicationSchedulerTests` / `MedicationSavePlumbingTests` pins are read first and never weakened.
- **Immediate visibility (owner report 2, display half):** `AppCoordinator.medicationEntries` is computed over the scheduler with no dedicated observable revision; the manage list's redraw on save must be explicit (a `@Published` revision bumped on the schedule-change seam and/or save completion), never incidental.
- **Root-cause verdict (required in the report + unit notes):** display-only vs real loss, with code-level evidence for both mechanisms (layout/redraw vs silent write), and which scenarios each produces on-device. The owner's build pre-dates W5/W6; device confirmation rides DV-1..DV-7.
- View-testable seams follow the `MedicationEditorSurfaceTests` precedent (static, testable functions + source pins) — do not invent a second testing style.
- `MedicationScheduleSettingsView`'s T-018 statics (`newDraft`, `draft(from:)`, `saveRequest(from:)`, `pendingRowFailureKey`, `switchToSlots/switchToTimes`) and the T-020 Medicine-times card/note stay where the shipped suites pin them; the conversion for row tap must call those statics, not a copy.
- The `.meds` route wiring is minimal: `SettingsTabs.swift` `case .meds` hosts the manage list; the editor is presented from there (the agent chooses the presentation mechanism that keeps the existing editor-surface suite green).
- Prefer existing catalog keys. A genuinely missing string is added in en+ne through the existing discipline, and the L10n pin is updated by re-measurement (count the added keys against the shipped catalog; update the medication family inventory and its pinned counts exactly).
- Same disclosure discipline as prior units: any deviation (including the editor presentation mechanism and any catalog key added) is recorded in the unit report and in `specs/implement-notes.md` at wave close.
- The only 40-char-token hazard discipline applies to any new file content (no exactly-40 contiguous alphanumeric token).
