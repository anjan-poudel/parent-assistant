## Description
Implement the video store exactly as design §5.2–§5.7: staging that creates a protected destination before any byte is written, streams bounded chunks, verifies protection after creation and after the stream, commits by same-volume rename, and sweeps pending and orphaned owners with a grace window. This unit is the sole owner of must-carry finding **B-3** and of the conditional-tolerance rule **R-5**.

## Acceptance criteria

```gherkin

  Scenario: The destination exists and is protected before the first byte arrives
    Given a staging call whose source will be streamed after file creation

    When staging runs
    Then staging returns protectionFailed

  Scenario: An unreported protection class is tolerated
    Given the platform reports no protection attribute at all
    When staging runs with an otherwise valid source
    Then staging succeeds
    And the reported class is recorded as unknown, not invented

  Scenario: A stream that fails mid-way leaves no accepted file
    Given a source that fails after the first chunk
    When staging runs
    Then the result is writeFailed with stagingFailed
    And no file under an owner root names the draft

  Scenario: Commit renames before the old file is deleted
    Given an owner with an existing instruction file and a staged replacement
    When commit runs
    Then the new path exists before the old path is removed
    And a failed new-path rename leaves the old file and the index unchanged

  Scenario: The sweep never deletes an unreadable source's bytes
    Given one readable owner list and one unreadable owner source
    When the orphan sweep runs with a 60 second grace
    Then files for the readable set follow the live rules
    And every file belonging to the unreadable source is kept
```

## Implementation notes
- **B-3 (review-l2 Condition):** follow design §5.2 steps 5–7 literally: validate the owner and filename, create the pending directory, create the destination file with `.completeFileProtection` *before* writing, stream in `stagingChunkBytes` (1 MiB) chunks, then re-verify. A reported class weaker than complete is `protectionFailed` and deletes. No `FileManager.copyItem` anywhere in this path.
- **R-5:** protection attributes are not reliably reportable on every supported OS. Treat "no attribute reported" as tolerable; treat a *reported weaker* class as a hard failure. This is a deliberate asymmetry, not an oversight.
- **N-1/N-4:** any empty, traversal-shaped, absolute or non-plain filename is refused with `deleteFailed` or `invalidOwner` before a URL is built, matching design §5.5.
- `stageSynchronously` is nonisolated but main-thread-only by contract. Do not dispatch it to a background queue; the chunk loop is bounded and the design's async bound is in the importer.
- `init` must perform no file IO (extend `NoIOInInitTests`). Base directory resolution is lazy, as design §5.1 requires.
- The in-flight commit set is `NSLock`-protected and consulted by `purgePendingDrafts`; do not use `@MainActor` state.
- `purgeOrphanedOwners(in:live:graceSeconds:)` takes the live set as an argument. It never reads the routine or event indexes itself.
- Attachments and thumbnails are out of scope.
