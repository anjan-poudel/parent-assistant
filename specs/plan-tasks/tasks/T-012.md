# T-012: Routine notification content builder and had_instruction payload

## Metadata
- **Group:** TG-04 — Routine and event owner seams
- **Components:** C17 (notification content builder), routine notification scheduler signature
- **Interfaces:** IF-30
- **Wave:** 0

## Owned files
- Creates `ios/ElderlyAssistant/Services/Notifications/RoutineNotificationContent.swift`.
- Extends `ios/ElderlyAssistant/Services/Reminders/RoutineAlarmScheduler.swift` (protocol parameter and delegation; no other behaviour change).
- Creates `ios/ElderlyAssistantTests/Services/Reminders/RoutineNotificationSchedulerTests.swift`.

## Description
Extract the pure routine-notification content builder so the payload is testable without a notification centre, and add the single `had_instruction` boolean to the scheduler's arming contract. Title, body, sound, identifier, the existing first-photo attachment and the absence of a category or action stay byte-for-byte equivalent to today's shipping behaviour.

## Acceptance criteria

```gherkin
Feature: Routine reminder notification content

  Scenario: The payload carries exactly the producer keys and one boolean
    Given a routine occurrence with a title and a visual aid
    When RoutineNotificationContent.make builds the content
    Then userInfo has occurrence_id, entry_id, type and had_instruction
    And had_instruction is the Bool passed by the caller
    And no instruction text, caption, filename or URL key exists
    And no category or action is set

  Scenario: A pre-upgrade payload without had_instruction reads false
    Given an armed notification whose userInfo has no had_instruction key
    When a reader resolves the value
    Then it reads false
    And a photo-only reminder's tap remains a no-op

  Scenario: The existing first-photo attachment is unchanged
    Given an entry with a first visual aid
    When content is built
    Then at most that one photo file is attached
    And an attachment factory returning nil leaves a text-only reminder
    And arming still succeeds

  Scenario: The builder never needs a notification centre
    Given the builder's injected attachment factory
    When the unit test builds content
    Then no UNUserNotificationCenter call occurs
    And the test asserts title, body, sound, userInfo and the absence of a category field by field
```

## Implementation notes
- Follow design §2.17 (C17), §3.6 (IF-30 declaration), §4.11 (tap context consumer), §11.3 H (payload), §11.3 S (taxonomy and scoped cancels). **N-6:** the suite is `RoutineNotificationSchedulerTests`; do not create or cite `RoutineNotificationContentTests`.
- The builder signature takes occurrence id, entry id, entry title, localized reminder title, first visual-aid URL, `hadInstruction`, and an injected attachment factory. It is nonisolated and pure.
- The scheduler protocol gains `hadInstruction: Bool` with **no default** (design R-3). `regenerateWindow` is the only production caller and is updated by T-013; this unit updates the protocol and the implementation delegation only.
- **FR-RIE-021/022:** no category, no action, no instruction text or media attachment. The only attachment remains the existing first photo. Keep scoped cancels exactly as they are; never call `removeAllPendingNotificationRequests`.
- **N-9:** the FR-RIE-015 evidence is that arming still happens with or without an instruction; do not make the builder or scheduler throw when instruction data is absent.
- Preserve the notification identifier format `routine_<uuid>` and the identifier used for cancels.
- Do not touch `NotificationCategories.swift`, medication scheduling or the event notification path.
