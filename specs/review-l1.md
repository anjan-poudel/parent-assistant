## Summary

The revised L1 design resolves all twelve iteration-1 findings. The architecture, scope, seams and the five accepted risks are retained. **B-1** is fixed by a synchronous pre-copy stat + metadata probe (duration, playability, video track) inside the picker/recorder callback, with the off-main importer kept as a second check and a store test proving a rejected source creates no staged file. **B-2** is fixed by the producer-constant `had_instruction` `userInfo` flag written at arm time plus a routine tap path that covers all three cases — instruction present, instruction removed, entry deleted — while a photo-only firing remains today's no-op. **M-1** is fixed by `InstructionWrite .set/.remove`, `nil` at the save seam meaning "leave untouched", and `InstructionDraft.resolvedWrite` gated on a terminal `.loaded` state with Save disabled while loading. **M-2** is fixed by the four-case `InstructionPlaybackAvailability` classification and a typed, PII-free `instruction_resolution` emitter that structurally accepts only `kind` + `outcome`. The eight minors are resolved with named interfaces, invariants, tests and risks.

No scope creep was found: no YouTube/link UI, no transcoding, no cloud, no medication path change, no new notification category/action/attachment, and exactly one instruction per owner. The only bound-file changes are the bounded `RoutineAlarmScheduler` `had_instruction` flag (text/body, banner/list/sound, first-photo attachment and scoped cancels untouched) and the one defaulted `timeText` parameter on the shared fired screen (nil at every medication and no-instruction call site). Both instruction handlers still return `false`, `NotificationFacade` still completes `[.banner, .list, .sound]`, and `NotificationCategories` is untouched.

A handful of non-blocking precision minors (N-1…N-5) remain; none contradicts a locked requirement, none blocks implementation, and each can be handled in design-l2 or in implementation notes. The decision is **GO**.

## Findings

### Iteration-1 findings — resolution status

#### B-1 — Pre-copy duration/playability enforcement (FR-RIE-006)

**Status: resolved.**

- D4 and D17 pin the ordering; §Capture "Video from the library" steps 2a–2d (design `:388–414`) and "In-app recording" step 3 (`:429–431`) require: stat the source and reject over-size; synchronously probe metadata (duration, playability, video track) and reject `.tooLong` / `.unsupportedFormat` / `.unreadableSource`; only then create the protected staged destination and stream-copy. The source URL is used only inside the callback.
- C02 `stageSynchronously(from:in:limits:prober:)` (`:934–1002`) fixes the order: (1) size stat and rejection, (2) `prober.probe` and rejection, (3) protected draft creation + copy + attribute verify, (4) return a staged handle whose filename is already plain. A rejection at (1) or (2) creates no directory and no file; a failure at (3) deletes the partial file and returns `.writeFailed`.
- C03 (`:1004–1054`) specifies the synchronous `InstructionVideoProbing` seam and keeps the async `InstructionVideoInspecting` importer as the second check under `validationTimeoutSeconds`; C04 (`:1056–1085`) requires both capture adapters to call `stageSynchronously` once inside the system callback, so no adapter can bypass the gate.
- Tests: `InstructionVideoStoreTests` (`:991–1002`) uses a scripted prober returning a 4-minute duration, an unplayable asset or no video track, and asserts `.tooLong`/`.unsupportedFormat` with a FileManager spy recording zero copies and no `_pending` file; over-size is rejected with no copy. `InstructionVideoImporterTests` covers the second-check cases.
- Risk 13 (`:1557–1564`) discloses the synchronous metadata read on the callback thread (main thread for `UIImagePickerController`): metadata-only, no frame decode, no copy, once per pick, with the heavyweight inspection off-main. The locked ordering is honoured as written.

#### B-2 — Routine tap/Open unresolved-owner/content branch (FR-RIE-019)

**Status: resolved.**

- D14 (`:80–81`) adds a producer-constant `had_instruction` Bool to the routine notification `userInfo`, written at arm time from `entry.instruction?.isPresent`. C17 (`:1416–1453`) specifies the pure `RoutineNotificationContent.userInfo(occurrenceId:entryId:hasInstruction:)` builder and the one added `hasInstruction` protocol argument; the notification title/body/sound, banner/list outcome, first-photo attachment and its throwaway copy, and the scoped-cancel identifiers are unchanged; no instruction/video URL is a parameter, so no video can reach `UNNotificationAttachment`.
- C11 (`:1266–1268`) passes `entry.instruction?.isPresent == true` at the existing `scheduleRoutineReminder` call (`RoutineScheduler.swift:366–372`), so every re-arm (launch, edit, set/remove) refreshes the flag.
- The tap resolution in §Fire-time (`:467–478`) covers the three cases: (1) `had_instruction == true`, entry resolves, instruction present → fired screen with title, delivery time and the playable card; (2) `had_instruction == true`, entry resolves, instruction removed → title + delivery time plus the plain localized `instruction.removed` fallback, no Play, no blank screen; (3) `had_instruction == true`, entry gone → plain localized `instruction.reminderUnavailable` notice with a Close control, no title/time claimed. `had_instruction == false` (photo-only or no instruction at arm time) remains exactly today's no-op. A missing key (notification armed before this release) reads as `false`.
- C14 (`:1322–1346`) specifies the routine `didReceive`: default action only, `had_instruction == true` only, resolve the entry (may be nil), main-queue `onInstructionTap(entryId, entry?, notification.date)`; always `false`. C15 (`:1360–1368`) maps `entry == nil` to `.unavailable` and `entry.instruction == nil` to `.missingInstruction`.
- Tests: `RoutineVisualAidFireHandlerTests` covers all three tap cases plus the photo-only no-op and always-`false`; `InstructionDisplayStateTests` proves `.missingInstruction`; `InstructionSurfaceTests` covers the `.unavailable` surface; `NotificationFacadeTests` / `NotificationCategoriesTests` run unchanged as the preserved baseline.
- Risk 14 (`:1565–1567`) records the pre-release-notification behaviour honestly: missing key = false, next launch re-arms and writes the flag, no migration and no false claim.

#### M-1 — Save-seam write semantics (InstructionWrite / hasChanges)

**Status: resolved.**

- D11 and D15 (`:74–79`); §Data model (`:258–303`) defines `InstructionWrite` as `.set(InstructionPayload)` or explicit `.remove`, **non-optional at the durable service seam**. There is no encoding in which nil or nil-kind means removal. `nil` exists only at the form/save seam and means "leave the instruction untouched".
- `InstructionDraft` carries `write`, `hasChanges`, `loadState` and `resolvedWrite = loadState == .loaded && hasChanges ? write : nil`. A loading or failed initial read can never produce a write. The event form disables Save while `.loading`; on `.failed` the instruction section is read-only with a plain message and Retry, while unrelated event fields remain saveable with `resolvedWrite == nil`.
- C10 (`:1199–1239`) specifies the event form's Save call and the nil / `.set` / `.remove` branches; C11 (`:1241–1273`) and C13 (`:1296–1315`) specify non-optional `setInstruction(_ write: InstructionWrite, ...)` on both services; C12 (`:1275–1294`) specifies `storeInstruction(_ instruction: Instruction?, ...)` where the optional is the payload reached only after an explicit `.remove`, not the save seam.
- Tests: `InstructionModelTests` pins the `resolvedWrite` truth table (loading/loaded/failed × hasChanges); `FreeFormEventServiceTests` covers nil-write leave-untouched, explicit remove, partial save and a failed index write; `FreeFormEventFormTests` proves a failed load passes nil and the stored instruction survives. Risk 15 (`:1568–1571`) records the mitigation.

#### M-2 — Resolution classification and PII-free logging

**Status: resolved.**

- D16 (`:83`); §Playback (`:591–634`) defines `InstructionPlaybackAvailability` (`.available(URL)`, `.rejectedFilename`, `.missingFile`, `.unreadableFile`) and `InstructionResolutionOutcome` (`rejected_name` / `missing` / `unreadable`). `InstructionVideoStore.availability(filename:for:)` (`:956–984`) classifies non-plain → rejected, absent → missing, present-but-not-readable-regular → unreadable, else available.
- The card maps the classification to the outcome, emits one `instruction_resolution` event with `kind` and `outcome` only, and renders the plain fallback; `.available` emits nothing. The typed emitter accepts only those two fields, so a filename cannot reach the event structurally, and a test additionally asserts the emitted metadata (`:608–615`, `:809–815`).
- `InstructionImageLoading -> Result<UIImage, InstructionImageFailure>` (`.rejectedFilename`, `.unavailable`) (`:617–634`) gives image loading an explicit success/failure result; the two adapters (`RoutineInstructionImageLoader` over `VisualAidStore` + entryId, `EventInstructionImageLoader` over `ContactPhotoStore`) both guard with `InstructionFilename.isPlain`; a `FakeInstructionImageLoader` scripts results in tests. Images emit `rejected_name` or `missing` (the umbrella for an unreadable image); `unreadable` is emitted only for video, where the seam can distinguish it. This is an honest limitation of the unchanged image stores, not a contradiction of FR-RIE-012's rejected-lookup clause.
- Tests: `InstructionVideoStoreTests` covers traversal (`../…`, absolute), absent, unreadable (directory at the path; `chmod 000`) and available — the three failures distinct; `InstructionDisplayStateTests` covers the mapping; `InstructionSurfaceTests` asserts no filename appears in the event.

### New findings (this review)

**N-1 — Delete-outcome wording overreaches the unchanged image stores (minor, clarity).** The lifecycle matrix says "delete old image file (Result)" and "delete event photo → delete instruction image ... (Result)" (`:361`, `:365`), and C13 says the cleanup uses "the `Result`-returning store methods" (`:1308–1310`). But `VisualAidStore.delete`/`deleteAll` (`VisualAidStore.swift:150–161`) and `ContactPhotoStore.delete(named:)` (`ContactPhotoStore.swift:136`) are Void and the design deliberately leaves those stores unchanged (`:1580–1582`). The Result/`deleteFailed` mechanics are implementable and required only for `InstructionVideoStore`; image-store delete failures remain the shipped best-effort no-ops. FR-RIE-014 requires deletion, not failure reporting, and m-2's taxonomy is satisfied by the video store, so this is not a locked-requirement conflict. Clarify in design-l2 that "Result" applies to video-store deletes only, so an implementer does not widen the shipped stores or claim an instruction-image delete failure signal that does not exist.

**N-2 — Observability wording overstates the emitter arrangement (minor, wording/gate coverage).** §Observability says "All instruction events are emitted through one typed emitter in a listed source root; shared files call typed methods and never build metadata themselves" and "No `FEATURE_EVENT_TYPES` entry is needed because every emitter lives in a listed root" (`:796–820`). C11, however, emits `entry_instruction_updated` through the existing `persistAndReschedule` in shared `Services/Reminders/RoutineScheduler.swift` with metadata `["kind": …, "count": …]` (`:1255–1260`). That file is not in `FEATURE_ROOTS` (verified `ios/tools/check-release-log-safety.py:184`), and the metadata is built in the shared file. The keys are allowed (`kind`, `count` in `LogSanitiser.allowedKeys`) and PII-free, and the gate's registry only requires each `FEATURE_EVENT_TYPES` entry to still be emitted, so the gate passes. Clarify that the new `instruction_*` events use the typed emitter in `Services/Instructions`, while `entry_instruction_updated` remains an existing shared-file observation; do not claim every routine event is gate-graded from a listed root.

**N-3 — Preflight-timeout ownership is stated twice (minor, implementability).** C06 says `InstructionPlaybackController` owns the timeouts and the state machine (`:1117–1119`); C07 says the AVKit adapter runs local-file preflight under `preflightTimeoutSeconds` (`:1133–1134`); the `InstructionVideoPlaying.present(url:title:completion:)` seam has no timeout parameter (`:646–651`). The controller receives the configuration, so either arrangement can be implemented, but an implementer could duplicate or omit the bound. Pin the owner in design-l2 — controller-enforced around the completion, or adapter-enforced with the configuration injected — while keeping the 0.6 s default and the 10 s ready watchdog as specified. This does not threaten NFR-RIE-008's 1 s bound because both values are explicit.

**N-4 — Implementation notes and citation drift (minor/notes).**

- `FreeFormEventService.save` returns `FreeFormEventSaveOutcome?` (`:1220–1231`); nil means the event save itself failed, while an instruction failure returns an outcome with `instructionSaved == false`. This matches the shipped `-> String?` shape and is tested, but the type's documentation should spell out the nil/partial distinction so callers do not conflate them.
- The capture protocols `InstructionVideoPicking` and `InstructionVideoRecording` are named but their signatures are not spelled out (C04). The coordinator tests use fakes and the UIKit adapters are device-smoke only, so this is not blocking; specify them in design-l2 for testability.
- Crash window: a process crash after the commit rename but before the index write can leave an unreferenced committed file. Normal failure paths delete it and the launch purge sweeps only `_pending` (`:352–354`); risk 16 covers a delete refusal, not a crash. This is a rare, bounded orphan; consider a launch sweep of unreferenced owner files in implementation or state the limit explicitly.
- `InstructionPayload: Equatable` relies on `UIImage` and `StagedInstructionVideo` being Equatable; declare the staged type's conformance explicitly.
- Citation drift (orientation-level; the design declares line numbers are not contracts): `EventExtrasStore.setPhotoFilename` is cited `:111–114`, actual `:110–113`; `AppCoordinator` routine-scheduler wiring is cited `:3583`, actual `RoutineScheduler(` at `:3571`; `ContentView` is cited `:65–72`/`:107–110`, actual routine overlay around `:61–69` and the event sheet around `:92–96`; C15 `:1362` writes `LocaleFormatters.shortTime(date, locale:)`, while the shipped API is `LocaleFormatters.shortTime(locale:) -> DateFormatter` (`App/ViewCaches.swift:51`, used at `RoutineSettingsView.swift:142`); the earlier §Playback reference `:488` uses the correct shape. Correct the one signature drift; the rest are anchors.


**N-5 — Preserved-baseline and gate-root wording (minor).** Two wording-precision points: (a) `App/InstructionCapture.swift` is described as "UI-layer, not in the log-gate logic roots" (C04 `:1058`), while §Observability explicitly says to add it to `FEATURE_ROOTS` (`:816`); the explicit gate plan is the operative one, and adding the file is consistent with the gate's role for new feature-owned UI sources. (b) m-4 says no-instruction routine call sites "render the same view tree as today", but the existing generic footer now carries an `InstructionCardView` whose `.none` state renders nothing; the rendered screen and the requirement's snapshot target are unchanged, while the view tree gains an inert view. Reword to "same rendered screen" (or keep `EmptyView` for `.none`) in design-l2. Neither point changes a locked requirement.

## Risks accepted

The five risks the iteration-1 review accepted are retained unchanged and remain accepted:

1. **D9 — instruction video is included in the normal iOS device backup (no `isExcludedFromBackup`). Accepted.** Parity with the shipped photo aids and encrypted payloads; no app network path; backup is OS-mediated. State it in the owner-facing report; backup-excluded media would be a scope change, not a design defect.
2. **D6 — the fired time is shown only when an instruction is present or expected. Accepted.** FR-RIE-017/020 require title and time on instruction-bearing firings while NFR-RIE-010 requires no-instruction firings to stay today's behaviour. The delivery-time source (`UNNotification.date`) is the honest "when this fired"; the scheduled-time alternative would require a further scheduler change and is not required.
3. **Event image instructions inherit `ContactPhotoStore`'s 512 px pipeline. Accepted.** FR-RIE-003 binds event images to the existing event photo path and forbids a parallel image store; the resolution consequence is a requirements consequence, not a design choice. Flag it to the owner for diagram legibility.
4. **Nested presentation — the playback cover lives inside the fired `fullScreenCover` or the event `sheet`. Accepted, conditional on the stated evidence.** The design checks the nested path first in the device smoke and names a bounded fallback (hoist the cover to `ContentView` through coordinator state) that does not change the injectable seam.
5. **Callback-scoped picker/recorder URLs. Accepted.** The PHPicker and `UIImagePickerController` URLs are valid only inside their callbacks; the synchronous `stageSynchronously` is the correct and only safe answer, and it keeps the rule in one place. The system UI cannot run in unit tests; the device smoke is the honest evidence.
