## Findings

- [MAJOR] **`measure_device.py` exit-code contract is wrong in three documents and untested.** Claimed: "exit 0 = gates pass, 1 = latency gate failed, 2 = malformed input" (measure_device.py:32; device-eval-protocol.md:16-18; specs/T-038-notes.md:72,83). Observed: missing file -> exit 1, malformed row -> exit 1, empty file -> exit 1 (`raise SystemExit("string")` yields status 1). Only argparse usage errors produce 2. Why it matters: automation cannot distinguish "no/bad device data" from "latency gate failed"; the phase's own claim is not exercised — tests assert `SystemExit`/message only, never `.code`, so a CLI-level code test would have caught it. Fix: print errors to stderr and `sys.exit(2)` for input/validation failures, keep 1 only for gate failure; add subprocess tests asserting 0/1/2.
- [MAJOR] **The device latency gate can pass vacuously on a tiny sample.** Reproduced: a 1-row measurements file (no `--prompts`) prints `latency gates passed`, exits 0 and appends an evidence row. With `--prompts`, missing ids only warn, never fail (score:130-138, main:209-211); `--replay` does not require `--prompts` at all. This contradicts the protocol's own "a pass is valid only if all prompts ran" (protocol:34) and spec's >=100 utterances; the cold/warm split is printed but not persisted in the evidence CSV. Fix: require `--prompts` (or an explicit partial-override flag), fail on missing ids and on incomplete/unknown coverage, and persist per-pass columns.
- [MAJOR] **Gemini-gap baseline has no corpus-revision binding, so a stale baseline can be silently used.** `read_gemini_baseline` matches labels only (eval_golden.py:501-522); `results.csv` rows appended with 6 columns carry no corpus hash (762-768); the manifest's `corpus_sha256` (781) is never read back. The task's implementation note ("record the corpus hash with every result row in `eval/results.csv`") is therefore unmet, and the committed smoke row has no committed sidecar. T-033-era rows sit on the old 20-row corpus (`results_manifest.jsonl` records corpus `1f4c059c…`; current corpus is `c5e4c049…`). Today the gate fails closed because no `gemini*` row exists, but the first later corpus extension would silently compare against a stale baseline. Fix: stamp the corpus hash into the label (or a row column/manifest join) and require the baseline's hash to equal the current corpus hash.
- [MAJOR] **Calibration has no minimum-sample policy despite the review requirement.** `calibration_stats` (450-469) treats n=1 identically to n=100; there is no stated or coded min-n, so a single consistent row can carry a bucket's PASS. Fix: define a min-n (e.g. n >= 5) — score only qualifying buckets, print/exclude insufficient ones, and fail when too much probability mass sits below the floor. Note: the Gherkin text only demands "per populated bucket", so this is a checklist-level requirement rather than a literal acceptance-criteria miss.
- [MINOR] Fixture backend silently degrades rows missing an `action` key to abstention (`pred.get("action", ABSTAIN_ACTION)`, used by all metrics); only missing ids are hard errors (298-305). Extra/unknown ids in a preds file are silently ignored. Fix: validate each replayed prediction has an `action` (and numeric confidence).
- [MINOR] `validate_rows` rejects overlaps only across different labels (402-405); same-label overlapping spans pass. Committed data is clean (scan found zero overlaps/adjacencies), so this is latent only; T-034 requires same-label adjacency merged at authoring.
