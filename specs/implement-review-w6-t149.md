## Findings

### N-1 — NOTE (rework-needed: no) — deviation 3, the `performLaunchFailHop` `.faceTime` leg does not thread the hop
The listing — and the implementation verbatim — calls `performFaceTimeCall(name: name, phone: phone, video: isVideo)` with no `hop:`, so a failed FaceTime hop candidate abandons its remaining suffix. Reachability probed: routed `.messenger` with candidates `[.faceTime, .phone]` is producible by the feature's own algorithm (`.anyChannel`, secondary `.faceTime`); with candidates `[.faceTime]` — every `.video` row — `remaining` is already `[]`, so the omission is invisible there. In this revision the only `performLaunchFailHop` callers are the openers' own failure branches and no call site passes a hop to them yet (the tap surfaces land in T-151/T-153), so the gap is unreachable in shipped behaviour today. Falsification attempt on the live path: the voice path with the same candidates does complete `[.messenger → .faceTime → .phone]`, because `hopFromCallAction` re-enters `performCallAction` with `hopCandidates: step.remaining` and the executor's own failure arms re-hop. Against the Gherkin, all asserted properties (≤ 2 steps, no repeats, ends on the shipped line, no re-entry) hold even in the abandoned-suffix case, so no acceptance scenario fails. Reading of intent: §10.1's `performFaceTimeCall` row ("shipped line, then hop") and §10.3's walk-to-exhaustion, plus the two sibling legs that DO thread (`hop: LaunchHop(candidates: step.remaining, handle: handle)` for `.whatsApp`/`.messenger`), make a one-line listing omission the most plausible intent — the `.faceTime` leg is the only asymmetric leg. Recommendation: amend the design record with the one-line fix (`hop: LaunchHop(candidates: step.remaining, handle: handle)`) and land it plus a tap-helper two-step pin with T-151/T-153, whose call sites make it live. As written, the implementation is faithful to the design text; no rework on T-149.
